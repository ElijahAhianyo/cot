## Project updates and stories

Future posts can introduce releases, discuss design tradeoffs, or describe a real application's lessons. Release announcements should link to the versioned [release notes](../../releases/overview/). Case studies should identify the application, its constraints, and the evidence behind any performance claims.

## Looking for help moving frameworks?

Use [Coming from another framework](../../coming-from/overview/) for the maintained explanation guides covering Django, Laravel, Rails, Spring Boot, Axum, and Actix Web. Those pages are organized by your starting point rather than publication date.

## Read a post in context

A design article explains a decision at a particular point in the project's development. A release announcement introduces a version. An application story describes one set of constraints. None is a substitute for checking the guide and API reference for the version you use.

Posts about an experiment should distinguish measured results from expectations. Posts about a proposal should identify what is implemented. That context lets readers enjoy a detailed story without having to guess which parts are safe to use in their application today.

## Find maintained answers

For routes, database behavior, and framework services, start with the [guides](../../guides/overview/). For a practical operation, use [how-to guides](../../how-to/overview/). For a new project, use the [tutorials](../../tutorials/overview/).

The blog lives in the site's main navigation because it is a separate reading destination. Documentation's sidebar stays focused on the versioned learning, explanation, task, and reference material.
